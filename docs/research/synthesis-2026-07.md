# AILang 综合判断 —— 两轮深度评审合并

**日期**：2026-07-27
**合并基础**：
- 第一轮「四个极致」深度评审（`docs/research/deep-review-2026-07.md`，commit `2f63e18`）——评**语言设计好不好**，8 视角 / 83 confirmed / 1 refuted，总判决 **5.25/10**
- 第二轮「规范工程成熟度审计」（本轮）——评**文档能否支撑独立团队实现编译器**，12 维 / 68 confirmed / 0 refuted，总成熟度 **5.2/10，约当 Rust 2010–2012 年（pre-alpha）**

**综合判据说明**：两轮数值接近（5.25 vs 5.2）但度量切面完全不同、**不互证**。综合的价值在于叠加——找出两套独立框架都命中的 gap（最高可信）、区分两类性质不同的问题、排出一份单一行动清单。

---

## 1. 一句话综合判决

**AILang 当前是「一份有稀缺亮点的设计文档」，但既不是「达成四个极致的设计」，也不是「可支撑独立实现的规范」——而且这两件事是同一件事：文档的承重缺口，直接就是设计的破洞。**

离两者都还差：一批纸面条款（未定义的地基）+ 一个被两轮都漏掉排第一的前提（规范治理地基）+ 少数几个需要重新决议的冻结决策。

## 2. 两轮切面互补（为什么必须合起来看）

| | 第一轮「四个极致」 | 第二轮「规范工程成熟度」 |
|---|---|---|
| **问什么** | 设计好不好（性能/AI友好/可观测/可预期） | 文档能不能支撑独立实现 |
| **视角** | 语言设计审查员 | 编译器实现者 / 规范工程师 |

| **最强项** | .ailmeta 元数据体系、错误全量建模、UB 收敛 | 数值语义闭合度、交叉引用零悬空、12 轮决议可追溯 |
| **最弱项** | 可观测运行期 2.5/10、性能锁死 Swift 档 | 常量求值域 ~5%、ABI/FFI 2.0、名字解析 2.0 |

**叠加洞察**：第一轮发现的设计破洞（如"语义类型运算断裂"），第二轮从规范工程视角给出了根因（"impl 求解算法 + 关联类型机制整体缺失"）。两轮是**症状（设计）与病根（文档）**的关系。

---

## 3. 核心洞察：问题分两类，修复成本天差地别

这是综合两轮后最重要的判断——**AILang 的问题不是一锅粥，而是两类性质完全不同的问题，该用完全不同的节奏处理：**

### A 类：未定义的地基（第二轮为主发现）—— 便宜、是编译器前置依赖
规范该写没写的承重条款：求值顺序、名字解析、字面量词法、conformance、数值转换算子、常量求值域……
- **修复成本**：多为纸面条款，每条一两行到一节；少数需一个设计决断。
- **紧迫性**：极高——现在不动编译器，实现者会自行发明这些决断并固化进编译器，未来补规范就是破坏性变更。
- **是否阻塞编译器**：是。词法器/解析器/类型检查器/借用检查器四个核心 pass 全卡在这类上。

### B 类：锁死的坏决策（第一轮为主发现）—— 贵、需要重新决议、不阻塞地基
已被 v0.2.1 冻结、但冻结方向本身有问题的决策：COW+原子 rc 唯一语义、borrow 彻底不逃逸、契约无构建分级、std.ai 语法冻结、溢出定性为"规范语义"。
- **修复成本**：高——需重新走决议流程，可能破坏冻结承诺。
- **紧迫性**：中——不阻塞编译器地基，但锁死性能上限、伤害"AI 原生"招牌。
- **处理时机**：可在 A 类补完后集中处理，部分（如 COW）可能要到 v0.3+ 甚至需要 RFC。

> **行动含义**：先修 A 类（便宜 + 阻塞地基），B 类排后。这和"哪类问题最严重"无关，和"哪类问题最该先动"有关。

## 5. 仅一轮命中的关键发现（互补部分）

### 仅第二轮（规范工程独有，第一轮完全没碰）
- **规范治理地基**：conformance 条款 / RFC 2119 规范性词汇 / normative-informative 分区 / glossary / RFC lifecycle / 语言级版本契约——**全缺**。这是"约当 Rust 2012 年前"判决的关键成因。
- **形式化层内核**：§27 控制流体产生式缺（if/for/while 是裸终结符）、typing rules / 推断算法 / soundness-decidability 声明缺、`<` 消歧规则缺。
- **名字解析算法**：编译器第一个语义 pass 却是最大盲区（§73 仅一行）。
- **借用检查器形式规则**：无 lattice/fixpoint/可判定性声明，"永久正确"是工程承诺非形式 soundness。
- **常量求值域**：五处用"编译期常量"零处定义，const fn/CTFE 整体缺失，全规范最薄弱单点（~5%）。
- **impl 求解 / 关联类型**：概念骨架在，但搜索算法/coherence/关联类型投影全空。

### 仅第一轮（设计独有，第二轮不评设计）
- **性能锁死**：COW+无条件原子 rc 是 string/List/Map/Set 唯一语义；borrow 彻底不逃逸致安全代码无零拷贝视图；契约无构建分级（无"验证换性能"回收路径）。
- **std.ai 空心**：自封"核心竞争力"，`agent.run` 连签名都没有，两处示例互相矛盾——对"AI 原生"招牌伤害最大。
- **语义类型运算断裂**：`type UserId = int` 后 `id1 == id2` 编译错且无解（旗舰特性"实现后必然导致别用它"）。
- **meaning 不可验证**却宣称"编译器验证后的事实"；**效果系统与运行时插桩结构性相斥**（pure 函数永不可加 print 调试）。
- **编译速度**未进入问题意识，冻结路线在复刻 rustc 慢编译的结构性成因。

## 6. 统一优先级清单（合并去重 + 按依赖重排）

两轮各自的 P0 合并后，**按"依赖关系"而非"严重度"重排**——这是综合后比两份报告单独看都进一步的关键判断：

> **P0-0 必须排第一**：第二轮发现，没有 conformance / RFC 2119 / 规范性词汇，连"补一条 typing rule 是 MUST 还是 SHOULD"都说不清——**规范治理地基是其他一切补齐的载体**。第一轮完全没意识到这一层，但它的缺位实际"卡住"了第一轮所有的 P0。

### P0-0｜规范治理地基（第二轮独有 · 一切前提）
新增 §1.5 Conformance + RFC 2119 规范性词汇 + normative/informative 分区 + 附录 D Glossary + 独立 RFC lifecycle 文档。
*不先做这个，下面所有补齐都无法定义约束力。*

### P0-1｜形式化层 + 名字解析（第二轮独有 · 编译器前三环）
- §27 补全控制流体产生式（if/for/while/loop + parallel for 表达式入口）
- §8.6 补全字面量词法（string/int/float/char + 进制 + 转义）
- §15.2 命名推断算法族 + 声明 decidability
- §27 增 `<` 消歧规则（推荐 `::<T>` turbofish）
- §12 增名字解析算法（作用域层级 + 点分路径 + .member 查找序）

### P0-2｜确定性 + 基础类型条款批（交叉印证 #1–#5, #10, #12 · 多为纸面条款）
- 求值顺序 = 左到右（逐产生式）
- locals 逆声明序 + 临时值构造逆序 drop
- UB / impl-defined / unspecified 三分法定义段
- Map/Set 迭代序决断 + Hash trait
- 数值转换算子（cast，float→int saturating）
- 字符串最小语义包（length 单位 + char + 迭代 + Eq 接地）
- build profile 正式定义（debug/release + overflow-checks）

### P0-3｜诊断 + 错误码 + TaskHandle 错误态（交叉印证 #7, #8 · AI-first 承重墙）
- §69.3 扩为 JSON 诊断协议（fix-it + applicability + expected/found）
- §18.2 落地 AIL2xxx 错误码注册表
- §17/§34 定义 TaskHandle 错误态 API + 死信（RFC 0003 已前向依赖）

### P0-4｜FFI/ABI + 供应链最小闭环（交叉印证 #6, #11）
- §25 扩为独立 ABI 章节（FFI-safe 白名单 + 调用约定 + 修正 printf 示例）
- lockfile 格式 + §42 签名/provenance + .ailmeta registry 重建为权威

### P1（重要但可在 P0 后启动 · 多为 B 类锁死决策或需 RFC）
- 并发内存模型（交叉印证 #9，需 RFC）
- 语义类型运算机制 impl+derive（仅 R1，兑现 §83#2 既定承诺）
- meaning 限制声明（仅 R1）
- 借用检查器形式规则 / 常量求值域 / impl 求解+关联类型（第二轮补漏，需 RFC）
- **B 类锁死决策**：COW 原子 rc / borrow 不逃逸 / 契约分级 / std.ai 拆薄 / 溢出定性——集中重新决议

## 7. 落到「文档 → 设计 → 实现」逻辑链

你的判断——"文档好了才方便设计，设计才会好"——被两轮数据精确验证：

| 环节 | 得分 | 状态 |
|---|---|---|
| 文档（规范工程成熟度） | 5.2/10 | 约当 Rust 2010–2012，骨架已具、内核未形 |
| 设计（四个极致达成度） | 5.25/10 | 蓝图局部领先，承重语义未定义 |
| 实现 | 0 | 无编译器 |

**文档分 ≈ 设计分（5.2 ≈ 5.25）不是巧合**——它印证了"文档厚度 ≈ 设计成熟度"：文档里没定义的承重语义（求值序、字符串、名字解析），直接表现为设计上的破洞（结果不可预期、trim 写不出、编译器无法开工）。**补文档 = 补设计 = 解锁实现**，三者是同一件事的三个切面。

> 这也是为什么两轮独立给出几乎相同的分数：它们度量的是同一个真实状态的两个投影。

---

## 8. 下一步建议

1. **先做 P0-0（规范治理地基）**——这是两轮都没给它排到第一、但综合后显然该排第一的事。没有它，后续补齐没有规范性约束力的载体。
2. **P0-1 到 P0-4 按"地基优先"顺序推进**，多为纸面条款或单一决断，无需等待外部研究。
3. **B 类锁死决策（P1）在 A 类补完后集中处理**，COW/std.ai 这类可能需要 v0.3+ RFC。
4. **P0 全部完成前，不启动编译器**——否则四个核心 pass 全卡或被迫自行发明决断，违背规范作为"可独立实现契约"的根本目的。

**一句话**：AILang 此刻最大的风险，不是某个具体缺陷，而是"蓝图领先"的叙事同时掩盖了"承重语义未定义"（第二轮）和"少数决策锁死了上限"（第一轮）。前者便宜且阻塞地基，必须先补；后者昂贵但可缓。
