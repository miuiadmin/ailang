## 1. 动机

两轮独立深度评审（设计 5.25 / 文档 5.2）合并后的**核心洞察**：AILang 的问题分两类——**未定义的地基**（便宜、阻塞编译器）与**锁死的坏决策**（贵、需重新决议）。而所有「未定义地基」类补齐的共同前提，是一层此前两轮都漏掉排第一的东西：**规范治理地基**。

**为什么治理地基必须排第一**。没有 conformance 条款，无法判断「何为合规实现」；没有 RFC 2119 规范性词汇，连「补一条 typing rule 是 MUST 还是 SHOULD」都说不清；没有 normative / informative 分区，无法区分「实现必须满足」与「仅说明」。换言之——**治理地基是其他一切补齐的规范性约束力载体**。spec-maturity 第二轮把治理三件套（conformance / RFC 2119 / normative-informative）列为全缺，正是「约当 Rust 2010–2012 年（pre-alpha）」判决的关键成因。

**本 RFC 填补的精确位置**。v0.2.1 冻结规范有 §1–§94 + 附录 A–C 的完整章节命名空间，但缺失五块规范工程元规则：

1. **Conformance 条款**——规范从未定义「何为合规 AILang 实现」。
2. **RFC 2119 规范性词汇**——正文使用「必须 / 应该 / 可以」（散见 Part 0 动机段：「必须」14 处、「应该」6 处含「不应该」、「可以」1 处）但无约束力等级定义。
3. **normative / informative 分区**——无法区分教程示例与强制规则（§44 约定、§45–§63 示例是否构成合规要求不明）。
4. **程序行为分类法**——§90 立场「安全代码永不 UB」存在，但 UB / 实现定义 / 未指定 三分法本身未建立（synthesis §4 交叉印证 #10）。
5. **build profile**——§90 #1 隐式使用 debug / release，但 profile 本身未定义（synthesis §4 #12）。

外加两块支撑设施：**Glossary 术语表**（资料性索引）与 **RFC lifecycle 文档**（本 RFC 之后所有变更的治理通道）。

**关键性质**：上述全部属**规范工程元规则层**，**非语言语义决断**——零新关键字、零新文法产生式、不改动 §83–§94 任一冻结决议。故可作为治理补齐**独立**合并，不与 v0.3+ 的语义特性 RFC（0001–0004）耦合。

## 2. 设计目标

1. **不触动冻结规范**——§1–§94 的语言语义、56 关键字、§83–§94 的 110 项可逆决议，**全部不变**。本 RFC 只新增元规则层内容（落地为 §1.5 + 附录 D + 独立 `docs/rfc-process.md`），不修改既有条款的语义。
2. **零新关键字 / 零新文法产生式**——`must`/`shall`/`should`/`may`/`conformance`/`normative`/`profile` 均**非关键字**（§9 的 56 不含其一，grep 确认）；不触动 §27 任何产生式。全部表面 = 规范正文文字 + 附录表格 + 独立文档。
3. **与既有冻结决议自洽**——本 RFC 定义的行为分类、build profile **必须**与 §90 #1（release 二补数回绕 / debug panic）、§90 #4（unsafe 精确清单 + FFI→abort）、§90 #5（字段 Drop 声明序）、§17（panic = 确定性栈展开 + 同序 Drop）完全对齐，不引入矛盾（§10 自洽核查表）。
4. **治理补齐非破坏性**——不升版本号（v0.2.1 维持）；版本演进留待 P0 路线（P0-0 → P0-4）完成时统一。
5. **最小自由度**——v0.2.1 当前**未**登记任何「实现定义行为」（目标是最小化此类自由度，对齐 Rust Reference 取向）；未来若引入须在附录登记。

## 3. Conformance：合规 AILang 实现

落地形态：规范新增 **§1.5.3**。

一个**合规的 AILang 实现**（conforming implementation）**必须**满足：

1. **接受并正确编译**所有符合 §27 形式文法、且**通过本规范全部规范性静态检查**（类型 §15、所有权 §18、效果 §19、契约 §20、可见性 §22 等——非穷举）的**安全代码**（safe code，即不含 `unsafe` 块的程序），并保证其行为符合本规范的规范性条款。
2. **遵守行为分类**（§6）：对安全代码，**不得**引入未定义行为。
3. **生成符合 §24 schema 的 `.ailmeta`**（随包强制产物，§32）——其字段集合遵循 §24（`.ailmeta` schema 的规范性来源），且输出**确定性**（固定字段排序）；该确定性要求由本条**确立为规范性义务**。（§78 仅为 Part IV 资料性的实现层排序描述，不构成本条义务的权威来源——见 §5。）
4. **诊断**违反规范性条款的程序（类型错误、所有权违规、可见性违规等），诊断信息**必须**结构化（**诊断发射协议**见 [RFC 0008](./0008-diagnostics-taskhandle.md) §4 的 JSON Lines 契约；§69.3 的内部 `Diagnostic` 结构为 Part IV 资料性参考，不构成本条义务的权威来源）。

> **引用纪律**：§3 的 MUST / SHOULD 条款以规范性来源（Part I 含 §27 / §15 / §18 / §19 / §20 / §22、§24、§32，及 §1.5 本节、RFC 0008 §4 协议等——非穷举）为权威；Part IV 的 §69.3 / §78 仅作资料性参考被提及，不因被本节引用而升格为合规要求（与 §5 的 normative / informative 分区一致）。

实现**可以**提供超出本规范的能力（扩展），但**不得**改变安全代码的规范性语义。`unsafe` 块（§25）与 FFI（`extern`，§25.3）是合规实现**唯一允许**偏离安全语义的逃生舱，其边界由 §90 #4 精确清单锁定。

> 对齐参考：Rust Reference「Conformance」、Go spec「Program execution」、C++ [intro.compliance]。AILang 的合规定义较窄——聚焦「安全代码的规范性保证」，因为 unsafe/FFI 是显式逃生舱（§25）。

## 4. 规范性词汇（RFC 2119 中文映射）

落地形态：规范新增 **§1.5.1**。

本规范采用下列规范性词汇表达约束力等级，含义对齐 IETF RFC 2119 / RFC 8174：

| 中文 | RFC 2119 | 约束力 |
|---|---|---|
| **必须** | MUST / SHALL / REQUIRED | 满足方为合规；违反即不合规 |
| **不得** | SHALL NOT / MUST NOT | 禁止该行为；违反即不合规 |
| **应** | SHOULD / RECOMMENDED | 强烈建议；偏离须有正当理由（对齐 RFC 2119 / 8174 SHOULD 语义） |
| **不应** | SHOULD NOT / NOT RECOMMENDED | 强烈不建议；偏离可有正当理由、不必定不合规——约束力**弱于**「不得」（绝对禁止），二者不可互替 |
| **可以** | MAY / OPTIONAL | 实现自由度；是否实现均合规 |

正文以中文词汇为准，附录 D（§8）给出完整术语映射。**仅当**上述词汇以**粗体**形式出现时，才具 RFC 2119 约束力（严格对齐 RFC 8174 的单一形式标记原则——ALL CAPS 在中文场景映射为**粗体**，以消除自然语言上下文判定的模糊；义务等级 MUST / SHOULD / MAY 由粗体关键词决定）；普通行文中的「必须」「可以」不自动升级为规范性语义。

> 设计选择（中文为主 + glossary 映射）：AILang 规范正文为中文，故正文用中文规范性词汇（必须 / 不得 / 应 / 可以），避免中英混杂；同时附录 D 给出 RFC 2119 英文映射，确保与 IETF / 编译器实现者社区的对齐无歧义。

## 5. 规范性内容与资料性内容（normative / informative）

落地形态：规范新增 **§1.5.2**。

- **规范性（normative）**：Part I 语言规范（§7–§27）、**Part II 标准库与包生态**（§28–§43——其中 §28–§42 为规范性核心：std.core / 标准库 API 签名与包模型；§43「生态优势」等纯论述段落为资料性；与冻结目录 Part II = §28–§43 一致，§9 / §28 段）、§24（`.ailmeta` schema）、§1.5（本节），以及 §83–§94 决议记录中标注 `[定义]` / `[语义]` / `[文法]` / `[schema]` / `[效果]` 的条款——合规实现**必须**满足。
- **资料性（informative）**：Part 0（§1–§6 动机与导览）、Part III（§44–§64 教程示例）、Part IV（§65–§82 编译器实现设计）、附录 A / B / C / D（D = 本 RFC 新增的术语表 Glossary，§8），以及决议记录中标注 `[示例]` / `[回归]` / `[一致性]` / `[完整性]` 的说明性条款——仅供理解，**不**构成合规要求。

**标签全集归类**（§83–§94 决议记录与正文所用的方括号标注，闭合 §3 引用纪律；复合标签采 `[A/B]` 单括号斜杠形式）：

| 标签 | 类别 | 说明 |
|---|---|---|
| `[定义]` `[语义]` | 规范性 | 锁定语言语义决断 |
| `[文法]` `[schema]` `[效果]` | 规范性 | §27 文法 / §24 `.ailmeta` schema / §19 效果系统 |
| `[示例]` `[回归]` `[一致性]` `[完整性]` | 资料性 | 示例 / 回归用例 / 一致性与完整性说明 |
| `[矛盾]` `[决断]` | **修饰类，不参与规范性判定** | `[矛盾]`=消解冲突的元记录、`[决断]`=确立某一决断——仅作过程/来源修饰；复合条目的规范性**只由上述 9 类内容标签决定**（§87 #1/#2、§88 #1、§93 #1/#2、§94 #3/#7 使用） |
| 复合标签（`[A/B]` 斜杠形，如 `[语义/示例]`、`[一致性/矛盾]`） | **任一规范性内容分量即整体规范性** | 复合判定只在 9 类内容标签间套用；`[矛盾]`/`[决断]` 分量被忽略（故 `[一致性/矛盾]` 仅按 `一致性`=资料性判定） |

> 规范性内容标签集合 `{定义, 语义, 文法, schema, 效果}` 为**闭集**——未列入该集合的标签（含 `[矛盾]`/`[决断]` 与任何新标签）一律不构成规范性分量。
- 资料性内容与规范性内容冲突时，以规范性内容为准。教程示例（§45–§63）为资料性；当示例与 Part I 规则不一致时，以 Part I 为准。

> 此分区直接回应 spec-maturity 第二轮「教程示例是否构成合规要求」的歧义，并把既有结构（Part 0/III/IV 本就是不同性质内容）形式化为规范条款。

## 6. 程序行为分类（定义 / 未定义 / 实现定义 / 未指定）

落地形态：规范新增 **§1.5.4**。**填补 synthesis §4 交叉印证 #10（UB 三分法未建立）。**

本规范对程序行为作如下分类。**上位分类（显式声明，消除术语碰撞）**：四类中，**定义行为**（窄义，见下首项：结果唯一确定）、**实现定义行为**、**未指定行为**三者统属**「非 UB 行为」**上位大类（均对结果施加某种约束、与 UB 互斥）；**UB** 是唯一「不施加任何约束」的类别。下文「定义行为」一词指**窄义**（四分法首项、结果唯一确定），「非 UB 行为范畴」指三者之上位——二者外延不同、勿混（对齐 ISO C/C++ 的 `well-defined behavior` 窄义 vs `defined behavior` 上位的区分惯例）。

- **定义行为（defined behavior）**：本规范完整规定结果，合规实现**必须**产生该结果。安全代码的算术（§90）、析构顺序（§18.7 / §90 #5）、错误传播（§17）等均属此类。
- **未定义行为（undefined behavior, UB）**：本规范不施加任何约束——程序进入 UB 后，实现**可以**产生任意结果（含看似正常、崩溃或错误结果），且**不**保证可观测的失败。**AILang 的立场：安全代码（safe code = 不含 `unsafe` 块的程序，§3）永不产生 UB。** （`extern` FFI 调用本身须置于 `unsafe` 块内 §25.1 ② 精确清单，故「不含 `unsafe` 块」已涵盖不含 `extern`——定义统一为单一条件。） UB 仅可能来自两类来源：① `unsafe` 块内对 §25.1 精确清单所列设施（裸指针 / `extern` fn / 标 `unsafe` 的 fn）违反其运行期操作前提条件的使用（含其触发的底层 UB，如裸指针解引用无效、调用原型不匹配的 `extern` fn 等）；注：在 `unsafe` 块**外**执行清单所列操作为**编译期错误**（非运行期 UB）；② 跨 `extern`（FFI）边界的不当交互（如 C 侧 `longjmp` 跨入，§90 #4）。**定义的逻辑结构**（消除「无约束即 UB」的反向误读）：上句「本规范不施加任何约束」为 UB 被归类后的**后果性质**（单向蕴涵：UB → 无约束），**非**「凡规范不约束者皆 UB」的成员准则；UB 的**成员准则**唯「仅来自 ①② 两类来源」（穷尽，双向：来源∈{①,②} ↔ UB）。未指定行为 / 实现定义行为同样不施加唯一结果约束，但属**非 UB 行为范畴**（允许若干合规结果之一 / 须文档化），**非** UB——故「结果不唯一」不等于 UB（资源耗尽见下注）。
- **实现定义行为（implementation-defined behavior）**：本规范要求实现**文档化**其选择，但允许实现间不同。v0.2.1 当前**未**登记任何实现定义行为（见设计目标 5）；未来若引入（如目标三元组相关的数据布局），**必须**在附录登记。
- **未指定行为（unspecified behavior）**：本规范允许若干合规结果之一，不要求实现文档化选择。当前主要未指定项：**表达式求值顺序**（实参、操作数、字面量元素的求值次序；除 `&&` / `||` 短路由语义内在规定外，未作规定）——此项**就地登记**于本节（§1.5.4「未指定行为」条目内），计划在后续 **P0-2** 收紧为左到右逐产生式求值（**不**入附录 B——附录 B 作用域声明为「编译器实现层遗留工程决断、非语言语义」，而求值顺序属语言语义的行为分类范畴，入附录 B 会与该作用域声明冲突）。**另一项未指定登记**：**资源耗尽（栈溢出 / OOM）与 double-panic** 亦归未指定（见下注——规范对其结果不施加唯一约束、不要求文档化，具体终止语义留 P0-3 收紧）。

> 注：`panic`（§17，含 `unwrap` / `assert`、debug 整数溢出、除零、越界、约束违约）是**定义行为**（确定性栈展开 + 同序 Drop），**不是** UB。此澄清对齐 §89 #3（panic 展开边界）与 §90 #4（panic 跨 FFI → abort）。

> 注（资源与展开失败——归入未指定行为，终止语义留 P0-3）：**栈溢出 / OOM**（资源耗尽）与 **double-panic**（panic 展开过程中 `Drop` / `Resource.release` 再次触发 panic）属**运行期 / 环境层**条件——规范对其结果不施加唯一约束、亦不要求实现文档化其选择，故二者**归入本节「未指定行为」类别**（与「表达式求值顺序」并列登记，见上）：允许若干合规结果之一，具体终止语义（abort / 未指定 / 等）**留给 P0-3 错误模型 RFC 收紧**——本治理 RFC 仅登记为未指定、不预设具体结果。**二者均非 UB**：UB 的成员准则穷尽为「仅 ① `unsafe` 块 §25.1 / ② `extern` FFI 边界 §90 #4」（见上 UB 条目），资源耗尽不属任一 UB 源——与「未指定行为 ≠ UB」一致（未指定是允许若干合规结果之一的**非 UB 行为**范畴，非「无约束」的 UB）。「安全代码永不 UB」指安全代码不触发 ①② UB 源，**不**就资源边界行为的结果是否唯一确定作承诺（资源边界行为归未指定，见上）——故合规实现在资源耗尽时可产生不同（未指定）结果，此为未指定行为的本质、非合规缺口。冻结 §17 当前承诺 panic 不传染进程（FFI 为唯一例外 §90 #4）；double-panic 是否构成该模型的边界扩展属 **P0-3 对 §17 的审查范围**，不在本 RFC 决断——本 RFC **不**开 §17 之外的新例外。

## 7. build profile（debug / release）

落地形态：规范新增 **§1.5.5**。**填补 synthesis §4 交叉印证 #12（build profile 未定义）。**

构建配置文件（build profile）控制编译期检查的强度与优化级别。合规实现**必须**支持至少两个 profile：

| profile | 语义 |
|---|---|
| **debug**（`ail build` / `ail run` 默认） | 开发期检测层**全开**：整数溢出 → panic `ArithmeticOverflow`（§90 #1）；契约 / 约束断言**必须**启用（§20 / §15.4）；边界检查启用——越界 panic `IndexOutOfBounds`（§17，**无条件**；§90 #4 指 unsafe/FFI 清单，非此）。 |
| **release**（`ail build --release`） | 优化构建：整数算术**二补数回绕**为规范语义（§90 #1），溢出 panic 关闭；**契约 / 约束断言无条件启用**（§92 #2 / §15.4 / §20，**不得**关闭、与 debug 同），不受 profile 调节。 |

- profile 的具体配置项（`opt-level`、`overflow-checks`）属工具链层，**应**在 `ail.toml` 的 `[profile.debug]` / `[profile.release]` 表声明（§30.1 待补，归 P0-2；具体 schema 见 [RFC 0007](./0007-determinism-batch.md) §9——**无 `debug-assertions` 项**，契约 / 约束 / `assert` / 边界检查均为**无条件**运行期检查）。
- **安全性不变量**：无论 profile，安全代码**不得**产生 UB（§6）。profile 仅调节开发期检测与优化级别，**不**改变安全代码的规范性结果（§90 #1 已锁定 release 回绕为规范语义，故溢出定性差异属规范许可、非 profile 引入的不一致）。

> 与 §90 #1 的关系：§90 #1 已分别规定 release 二补数回绕（规范语义）与 debug 溢出 panic（开发期检测层），但未给 profile 本身命名或定义可配置项。本节把 §90 #1 隐式使用的 debug / release 提升为正式 profile 概念，二者完全自洽、无新决断。

## 9. RFC lifecycle（独立文档）

落地形态：规范引用的**独立文档** `docs/rfc-process.md`（不进 AILANG.md 正文，因其定义 RFC 自身的流程，作为独立治理基础设施更合适）。

定义 AILang 设计提案（RFC）从 **Draft → Review → FCP → Accepted → Implemented** 的生命周期，含：

- **状态机**：Draft（起草）/ Review（公开 + 对抗式 workflow 审查）/ FCP（最终评论期）/ Accepted（采纳待实现）/ Implemented（合并进规范或编译器）/ Rejected / Postponed / Withdrawn。
- **编号与文件**：连续四位 `NNNN`，路径 `docs/rfc/NNNN-kebab-title.md`；头部**必须**含标题、状态、版本（Draft vN）、关联 P0/P1 分级、是否触动冻结规范、是否新增关键字 / 文法产生式。
- **采纳标准**：自洽（与 §1.5 / §17 / §90 无矛盾）+ 可对抗验证（收敛 0H/0M/0L）+ 冻结影响声明 + 实现可行性。
- **规范解冻通道**：对冻结规范的直接修改**应**经一份 Accepted RFC 授权；或属 P0-0 类治理地基补齐（不改语义决断、不增关键字 / 产生式）并显式登记于附录 A、版本号维持不变。

> 历史决议记录（§83–§94，记录 I–XII）是本流程建立前的既有沉淀，其权威性不受影响。RFC 0001–0004（Draft）在本流程下状态不变。

## 12. 与既有决议的关系 / handoff

- **不触动 §83–§94 任一冻结决议**——本 RFC 是元规则层，不重新讨论任何语义决断。§90 #1/#4/#5、§17、§25.1/§25.3 等均作为**既定前提**被引用，不被修改。
- **与 RFC 0001–0004 正交**——四份特性 RFC 均声明「不触动冻结规范、零新关键字」，本 RFC 为它们提供**规范性约束力的形式化载体**（conformance + RFC 2119）。合并本 RFC 后，0001–0004 的条款在 Implemented 时可被明确标注 MUST / SHOULD。
- **解锁 P0-1～P0-4**——synthesis §6 的后续 P0（形式化层 / 确定性条款 / 诊断协议 / FFI）在补齐时，每条 typing rule、每条求值顺序决断都可落在 §1.5 提供的规范性词汇框架内（MUST / SHOULD / MAY）。
- **schema_version 无关**——本 RFC 不改 `.ailmeta` schema（§88 #2 的 `0.2.0` → `0.3.0` 升级由 RFC 0001–0004 的 `examples[]`/`contracts`/`properties[]` rider 承担，与本 RFC 无关）。

## 13. 开放问题

1. **求值顺序收紧时机**——§6 登记「表达式求值顺序未指定」为遗留，计划 P0-2 收紧为左到右。本 RFC 仅登记现状，**不**预先决断收紧方向（留 P0-2 单独 RFC 或决断）。
2. **`ail.toml` profile 表**——§7 指明 profile 配置项属工具链层、归 §30.1（P0-2）。本 RFC 不定义具体配置项 schema。
3. **实现定义行为登记表**——设计目标 5 声明 v0.2.1 未登记任何实现定义行为；未来引入时的附录登记格式待定（新增附录 E 或等价的语言语义层登记位）。实现定义行为属 §6 语言语义分类（规范要求实现文档化其选择），**不入附录 B**——附录 B 作用域为「编译器实现层遗留工程决断、非语言语义」（同 §6 求值序论证）。

## 14. 收敛轨迹

**Draft v1（本文）**——尚未跑对抗式 workflow。计划按 RFC 0001–0004 既有流程：多维度 workflow 审查（建议维度：自洽性 / 冻结边界 / 交叉引用悬空 / 与 §90 §17 §25 对齐 / 中文术语一致性 / RFC 2119 映射准确性 / glossary 完备性 / normative-informative 划分正确性）+ 对抗式 verify，目标收敛 **0H / 0M / 0L**。

> 由于本 RFC 是元规则层（无代码、无文法、无算法），验证重心在**规范文本自洽与交叉引用完整性**，而非 0001–0004 的实现可行性——这降低了验证复杂度，预期收敛轮次少于特性 RFC。
